# テストの作り方

このライブラリの回帰は、繰り返し同じ形で起きてきました。この文書は、その形を捕まえられるテストの条件をまとめたものです。**新しいテストを書く前に必ず読んでください。**

## 絶対に守る 3 つの規則

### 規則 1: 期待値は仕様書から取る。実装から取らない

期待値の根拠は `docs/ja/specs.md` の記述です。**実装の現在の挙動を写してはいけません。**

やってはいけないこと:

- テストを書いて落ちたから、通るように期待値を下げる
- 実装のソースを読んで「こう動くはずだ」と期待値を決める
- 不変条件が現在のコードに合わないので、条件を緩める

仕様書に書かれていない場合は、**期待値を決めずに人間へ確認してください**。実装に合わせて決めると、不具合をそのまま仕様として固定してしまいます。

テストのコメントには、根拠にした仕様書の**節の見出し**と引用を書いてください。後から読む人が、それが仕様由来か実装由来かを判別できるようにするためです。

**行番号で参照しないでください。** 仕様書へ 1 行足すだけで、それ以降のすべての参照が別の行を指します。実際に 2026-08-04 の棚卸しで、約 30 箇所のうち 10 箇所ほどが無関係な行を指していました。

書式は次のとおりです。

- **節の参照**: `仕様` の直後に 1 つめの `「」` を置き、中身を `docs/ja/specs.md` の見出しと**文字どおり一致**させる（`data-each-visible` のように括弧付きの見出しは括弧まで含める）
- **本文の引用**: 節の参照に続けて 2 つめ以降の `「」` に置く。`仕様` の直後へ引用を置かない（下の検査が節名と区別できなくなる）

```
良い例: 仕様「反映待ちの間に起きた変化」の「最後に供給された値が…残ります」
悪い例: 「仕様」の直後に本文の引用を置く（検査が節名と区別できず、常に 1 件報告する状態になります）
```

2026-08-06 の後追いで、**全テストファイル（151 件）に参照を書きました**（参照 323 件はすべて見出しと一致）。仕様書に根拠が無いものは、そのことを本文に明記しています。この後追いで見つかった仕様書の空白は次の 2 件で、いずれも実装契約として固定してあります。

| 事象 | 対応するテスト |
| --- | --- |
| `haori:bindcomplete` の発火時点（`data-if` / `data-each` の DOM 反映との前後） | [tests/bindcomplete-and-scope.test.ts](../../tests/bindcomplete-and-scope.test.ts) |
| `data-if` による表示（`haori:show`）を契機に `data-load-*` が発火すること | [tests/data-load-on-show.test.ts](../../tests/data-load-on-show.test.ts) |

次のコマンドで全参照を検査できます（テンプレートリテラル内のエスケープを外して比較します）。

```powershell
$h = Select-String -Path docs\ja\specs.md -Pattern "^#{2,6}\s+(.+)$" |
  ForEach-Object { $_.Matches[0].Groups[1].Value.Trim() }
Select-String -Path src\*.ts,tests\*.ts,tests\helpers\*.ts,docs\ja\*.md `
  -Pattern "(?:仕様|同)\s*(?:の)?\s*「([^」]+)」" -AllMatches |
  ForEach-Object { $_.Matches } |
  Where-Object { $h -notcontains $_.Groups[1].Value.Replace('\', '') } |
  ForEach-Object { $_.Value }
```

### 規則 2: 修正前のコードで落ちることを確認する

回帰テストは、**修正前のコードで落ちること**を確認してから追加してください。落ちないものは回帰テストとして数えません。

確認の手順:

1. 対象の修正を一時的に無効化する（該当の分岐を早期 return させる等）
2. 追加したテストを実行し、**落ちること**を確認する
3. 一時的な変更を戻す（`git checkout -- <file>`）
4. テストが通ることを確認する

2 で落ちない場合、そのテストは何も守っていません。観測点や観測方法を変えるか、テストを捨ててください。件数を増やすだけのテストは、カバレッジの数字を上げながら「守られている」という誤った印象を与えます。

### 規則 3: 足した行は、外すと落ちるテストで必要性を確かめる

規則 2 の裏返しです。規則 2 はテスト側の検出力を確かめ、**規則 3 は実装側の各行の必要性を確かめます**。修正で足した行・条件・分岐は、**1 つずつ外して（またはひっくり返して）テストを実行**し、どのテストが落ちるかを確認してください。

確認の手順:

1. 足した行を 1 つ外す（条件なら反転させる）
2. 関連するテストを実行し、**どれが落ちるか**を確認する
3. 元へ戻す

落ちるテストが無かった行は、**必要性が確かめられていない行**です。次の 3 つから選んでください。

| 状況 | 対応 |
| --- | --- |
| 仕様に根拠があり、観測できる差もある | その行を守るテストを足す（規則 2 の手順で、行を外すと落ちることを確認する） |
| 観測できる差が無い（他の行が結果を決めている） | **行を削る。** 削った理由をコメントに残す |
| 仕様に根拠が無い | 削る。必要だと思う理由を人間へ確認する |

**「念のため」の行を残してはいけません。** 0.41.2 では、必要性を確かめずに足した 1 行が別の経路の権威判定を狂わせ、報告 AJ（貼り付け・IME 確定の消失）を招きました。守るテストが無い行は、誰にも気づかれずに次の回帰の原因になります。

実例（2026-08-06、群の範囲の修正）: 足した 4 つの判定を 1 つずつ外し、それぞれ 1 件のテストが落ちることを確認しました。下向きのフォーム境界の刈り取りだけは**外しても結果が変わらない**（範囲の解決が結果を決めていた）ため削り、その理由を関数のコメントに残しています。

## 過去の回帰の形

これまでの不具合はほぼすべて「**非同期の段 A が、別の段 B がすでに進めた状態に対して走る**」という形でした。バインドデータの更新は次の段を重ねて進みます（仕様「`data-{event}-reset`」）。

```
data-bind 属性の反映 → 入力欄への書き戻し → 再評価（data-each の行生成） → 載らなかった書き込みの載せ直し
```

段の数だけ「途中まで正しく、次の段で壊れる」余地があります。

### 最終状態を見るなら `waitForIdle()` を使う

`Queue.wait()` は**呼び出し時点のキュー内容だけ**を待ちます。「1 段の完了を待ってから次の段を積む」直列チェーン（`Form.reset()` は 8 段ある）では、固定サイクル数の `waitForDomSettled()` は処理の途中で解決します。

これで実際に**2 件の誤検出**を出しました。`Form.reset()` の各段を計測したところ、`afterEach` で DOM を消した後もリセットが動き続けており、テストは「まだ処理中」の状態を「仕様違反」として報告していました。

```ts
// 悪い例: リセットが終わる前に判定する
resetButton.click();
await waitForDomSettled(12);   // ← 8 段のうち 3 段目あたりで解決する
expect(input.value).toBe('初期');

// 良い例: 追従して積まれる処理まで含めて落ち着かせる
resetButton.click();
await waitForIdle();
expect(input.value).toBe('初期');
```

**最終状態を検証するテストでは `waitForIdle()` を使ってください。** 逆に、修復前の中間状態を狙って観測するテスト（[tests/row-identity.test.ts](../../tests/row-identity.test.ts)）は固定サイクルの `waitForDomSettled()` のままにします。`waitForIdle()` へ替えると中間状態が観測できず、検出力を失います。

### 待ち合わせの条件は最終状態そのもので書く

`waitForCondition()` の条件を「部分的に成立する指標」で書くと、途中の状態で成立して先へ進みます。

```ts
// 悪い例: 行の要素が生えた時点で成立し、行内の {{r.name}} は未評価のまま進む
await waitForCondition(() => rowLabels().length === 2);
expect(rowLabels()).toEqual(['新一行目', '新二行目']);   // ← ここで落ちる

// 良い例: 検証したい最終状態そのものを条件にする
await waitForCondition(() => rowLabels().join('|') === '新一行目|新二行目');
```

行数・件数・存在の有無は、たいてい「描画の途中でも成立する指標」です。

### 余裕の棚卸し（固定サイクル依存の検出）

固定サイクルの待機は、**必要サイクル数がちょうど既定と同じ**になっていても緑のまま通ります。この状態は、製品側の段が 1 つ増えるだけで落ちます。前提の組み立てに使っていると、本題と無関係な理由で落ちるため原因の特定に時間を取られます。

読解では見つからないので、**既定サイクル数を下げて計測**します。

```
tests/helpers/async.ts の waitForDomSettled(cycles = 3) を一時的に 2 へ下げ、
フルスイートを実行する。落ちたテストが「余裕ゼロ」の集合である。
```

**判定基準: 既定を 1 つ減らしてもフルスイートが緑であること。** 緑でなければ、落ちた箇所の待機が「前提の組み立て」なのか「中間状態の観測」なのかを判定し、前者なら `waitForIdle()` へ替えます。

2026-08-04 時点の計測値は次のとおりです。棚卸しをやり直したらこの表を更新してください。

| 既定サイクル | 結果 |
| --- | --- |
| 1 | 8 件失敗（2 サイクルを要する。既定に対しては余裕があるので据え置き） |
| 2 | 全緑（判定基準を満たす） |
| 3（既定） | 全緑 |
| 6 | 全緑。**DOM の中間状態を狙うテストで 6 以下に依存しているものは無い** |
| 12 | 1 件失敗（`tests/poll.test.ts`。ポーリング間隔への依存で、DOM の段数とは別の理由） |

**既定を上げて済ませてはいけません。** 上げると、中間状態を狙うテストの検出力を将来にわたって削ります。落ちた箇所を個別に直してください。

### したがって、操作の間に `await` を挟むと不具合は再現しません

これが以前のテスト群の致命的な欠陥でした。各操作の間で settle を待つと操作が直列化し、割り込みが原理的に起きません。**割り込みを検証するテストでは、操作の間に `await` を挟まないでください。**

```ts
// 悪い例: 直列化されるため、割り込みの不具合は絶対に再現しない
form.setAttribute('data-bind', '{"keyword":"外部"}');
await waitForDomSettled();          // ← これが不具合を消す
input.value = '編集';
input.dispatchEvent(new Event('change', {bubbles: true}));

// 良い例: 割り込ませる。await あり版も別途書いて、両方の列を押さえる
form.setAttribute('data-bind', '{"keyword":"外部"}');
input.value = '編集';
input.dispatchEvent(new Event('change', {bubbles: true}));
await waitForDomSettled(12);
```

権威規則（どちらの値が残るか）は仕様「ユーザー編集と宣言バインドの権威」「反映待ちの間に起きた変化」に定義があります。組み合わせの網は 2 つの軸に分かれています。

| 軸 | ファイル | 足すとき |
|---|---|---|
| 供給手段（`data-bind` 書き換え / `Core.setBindingData` / リセット …） | [tests/interleaving-authority.test.ts](../../tests/interleaving-authority.test.ts) | 新しい供給手段を追加したら `SUPPLIES` へ 1 行 |
| 入力手段（`change` を伴う編集 / 打鍵 / 貼り付け・IME 確定 / イベントを伴わない代入） | [tests/input-method-authority.test.ts](../../tests/input-method-authority.test.ts) | 新しい入力手段を扱えるようにしたら `INPUT_METHODS` へ 1 行 |

**入力手段の軸が無かったために回帰が続きました。** 報告 AA（スクリプトの代入）・AG（外部ライブラリの代入と打鍵）・AJ（貼り付け・IME 確定）はいずれも**値の入り方**が軸で、供給手段の網だけでは別の入り方から同じ規則が破れます。導入時、この網は初回で 2 件の不具合（リセット中の打鍵・貼り付けの消失）と 1 件の仕様の空白（属性書き換えと同一マイクロタスク内の入力の優先順位）を検出しました。

**1 つの規則には、それを破りうる侵入口が複数あります。** 報告された侵入口だけを塞ぐと、隣の侵入口から次の報告が来ます。報告を直したら「同じ規則を破れる別の経路はどこか」を必ず数え、軸として網にしてください。

### 人工的な状態を作らない

割り込みは、**利用者や外部スクリプトが実際に行える経路**で起こしてください。内部メソッドを直接呼んで in-memory だけを進めるようなテストは、実際には起こらない状態を作ります。

過去に `ElementFragment.setBindingData()` を直接呼んで割り込みを模したテストがあり、そのために**生きた不具合を隠していました**。実イベント（`change`）へ書き換えた途端に落ちました。

## 不変条件の常時検査

[tests/helpers/invariants.ts](../../tests/helpers/invariants.ts) が、仕様から取った不変条件を持っています。`waitForDomSettled()` の終わりで自動的に検査されるため、**個々のテストへ検査を書き足す必要はありません**。

| 条件 | 内容 | 根拠 |
|---|---|---|
| I1 | `data-bind` 属性 == in-memory のバインドデータ | 仕様「`data-bind`」 |
| I2 | `data-each` が描いた行数 == 配列の要素数 | 仕様「`data-each`」 |
| I3 | 行 i のリストキー == 配列要素 i から作るリストキー | 仕様「`data-each`」 |
| I4 | 収集値 == バインドデータ（`expectCommitted()`、確定後のみ） | 仕様「双方向バインディングの自動更新」 |
| I5 | 入力欄の内部値 == バインドデータの同じ経路の値（DOM が先に進むのは正しい） | 仕様「収集は DOM を真とする」 |

**I5 は「内部値をバインドデータより先に進めない」条件です。** 先に進めると、続く逆方向同期が古いバインドデータを不一致とみなして入力欄を上書きし、入力した値が表示からも収集値からも消えます（仕様が同節でこの故障をそのまま説明しています）。報告 AJ はこの条件を破った回帰で、**I5 を入れた状態で 0.41.2 のコードを走らせると、AG の回帰テスト（`tests/pending-write-typing.test.ts`）の中で落ちます**。つまり作り込んだ時点で捕まります。

比較の相手は「実際に入力欄へ流し込まれる値」に限ります。対象と除外は `collectInternalValueLeads()` のコメントにあり、**除外はすべて仕様の記述に対応させてあります**（宣言バインドを持つ欄、フェッチを起こす欄、行データが権威の行、逆方向同期を受けないフォームなど）。導入時の棚卸しでは 16 件が発火し、10 件が `data-form-arg` フォームの「フォーム自身のコピー」、5 件がフェッチ飛行中、1 件が実在の不具合（リセット中の非 `change` 入力の消失）でした。**除外を足すときは、対応する仕様の記述を必ず添えてください。** 記述が無ければ、条件を緩める前に不具合として報告します。

I1 の除外は**仕様が明記した 2 種類だけ**です（`_` 始まりの予約キー: 仕様「`data-fetch-state` / `data-{event}-fetch-state`」「`data-poll-state`」、`data-each-visible` の可視範囲: 仕様「`data-each-visible`（スクロール追従の可視行範囲）」）。**ここを増やしてはいけません。** 増やすとミラーの取りこぼしを検出できなくなります。

意図的に不整合な状態を作る必要がある場合は、`exemptFromInvariants(element)` で範囲を要素単位に絞り、**外す理由をコメントに書いてください**。`setInvariantMode('off')` は文書全体を止めるため最後の手段です。

環境変数 `HAORI_INVARIANTS` で切り替えられます（`assert` 既定 / `report` 棚卸し用 / `off`）。棚卸しには `report` を使ってください。

## 効かなかった方法（再発明しないために）

**待機サイクル数を 1 周期ずつ振って観測する方法は、行の取り違えを検出できませんでした。** 「期待値へ到達し、到達後は離れない」という条件では、到達までの誤った期間をいくら長くても許してしまいます。`data-each-done` が付いた周期だけを見る条件を足しても、行の取り違えは完了マーカーが付く前に自己修復されるため、やはり落ちませんでした。

このクラスは、`waitForDomSettled(8)` のように**修復前の周期を狙い撃ちする**既存の書き方（[tests/row-identity.test.ts](../../tests/row-identity.test.ts)）でしか捕まっていません。より良い観測方法は未確立です。
